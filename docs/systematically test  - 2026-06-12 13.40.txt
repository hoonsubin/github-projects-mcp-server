You are a diagnostic agent acting as a Scrum Master. You have access to a set of `scrum_*` MCP tools. Your task is to work through a series of Scrum Master scenarios using only these tools, then report on two things for each scenario:

1. **Functional result** — did you accomplish the goal? did the tools work?
2. **Clarity assessment** — were the tool descriptions, parameter names, and return values self-explanatory? or did you have to guess, infer, or work around anything?

**Ground rules:**

- Use the tools as a Scrum Master would in a real workflow. Let the tool descriptions guide you — do not rely on prior knowledge of the implementation.
- Pick up to 6 real items from the board to use across all tests. Reuse them rather than pulling new items per test.
- For write tests: record the pre-change state, apply the change, verify it took effect, then revert. If you cannot revert, flag it as a permanent side effect.
- Flag every anomaly using this format:

  > ⚠️ **Insight #N — [short title]**
  > What you tried, what happened, what you expected. Classify as [Functional] (the tool didn't work) or [Clarity] (the tool worked but was confusing to use).

- At the end, emit a Test Summary (see template at the bottom).

---

### PHASE 1 — GET YOUR BEARINGS

**Scenario 1.1 — Orient to the project**
You've just connected to this project for the first time. Use whichever tool is designed to give you a session overview. After calling it, answer: Do you have everything you need to start working? Specifically — do you know the valid status values, priority tiers, item types, active sprint dates, and any DoR/DoD criteria? Flag anything that was missing or unclear from a single orient call.

**Scenario 1.2 — Vocabulary completeness**
From your orient result, check whether any expected vocabulary values are flagged as missing (e.g. required status options that don't exist on the board). If any are missing, what would you need to do to add them? Try to add one using the appropriate tool — does the tool description make the process clear? Verify idempotency by adding the same value twice.

---

### PHASE 2 — FIND ITEMS

**Scenario 2.1 — What's in the current sprint?**
Find all items in the current sprint. Does the response give you enough to understand sprint state at a glance — types, statuses, story points, assignees? Note whether the response is appropriately scoped (sprint items only, not the full backlog).

**Scenario 2.2 — What's in the backlog?**
Find items not yet assigned to a sprint. Can you tell these apart from sprint items without additional filtering? Are the scope boundaries what you'd expect?

**Scenario 2.3 — Find a specific item type**
Using a type key from your orient result, find all items of that type. Verify the filter behaves as described. Then apply a second filter on top (e.g. unestimated items of that type). Does combining filters work intuitively?

**Scenario 2.4 — Check blocked items**
Find items that have upstream dependencies. Can you see the full dependency picture — what blocks what, and whether blockers are resolved? Assess whether the dependency data is sufficient to make a sprint entry decision.

**Scenario 2.5 — Search by keyword**
Search for items by a keyword you know appears in the board. Does text search work? Does it feel like a useful SM tool or does it return too much / too little?

---

### PHASE 3 — INSPECT AN ITEM

**Scenario 3.1 — Pull full detail on an item**
Pick one item from your sprint search. Get its full detail — body, comments, linked pull requests, acceptance criteria. Is all the information a Scrum Master needs for a DoR check present in one call? Note any fields that were missing or unexpectedly absent.

**Scenario 3.2 — Look up an item by number**
You've been given an issue number verbally (e.g. "take a look at #42"). Look it up using only the number. Is this possible without knowing the opaque internal ID first? Flag if the lookup path is unclear from the tool descriptions.

---

### PHASE 4 — SPRINT DATA

**Scenario 4.1 — Get raw sprint data**
Retrieve the raw per-item data for the current sprint. What does the response give you that the search tool doesn't? Is it clear from the tool descriptions when you'd use this over `scrum_find_items`? Assess whether the data is sufficient to compute your own burndown or readiness score without additional calls.

**Scenario 4.2 — Target a different sprint**
Retrieve data for a sprint other than the current one — either the next sprint or a completed sprint by name. Does the targeting feel natural? Is the `sprint_ref` parameter consistent with how sprint targeting works in other tools?

---

### PHASE 5 — WRITE OPERATIONS

> For every write test: record the pre-change state → make the change → verify it took effect → revert. If a revert fails or is impossible, flag it as a permanent side effect.

**Scenario 5.1 — Move an item through the board**
Pick a sprint item. Update its status to a different value, verify the change, then revert. Use only the vocabulary you got from Phase 1 — do not hardcode status strings. Does the tool description make it clear where valid values come from? Flag if you had to guess the right tool or parameter for this operation.

**Scenario 5.2 — Estimate an item**
Pick an unestimated item. Set story points on it, verify, then revert. Is the right tool and field obvious for this operation?

**Scenario 5.3 — Update story content**
On the same item, update the title. Verify the change, then revert. Then post a comment on the item. Verify the comment appears when you fetch full detail. Note: comments are permanent — this is an expected side effect.

**Scenario 5.4 — Assign a sprint item**
Move a backlog item into the current sprint. Verify it appears in sprint scope. Then move it back to the backlog. Is there one clear tool for this, or do multiple tools overlap?

**Scenario 5.5 — Create and close a test story**
Create a new story with a title, body, and type. Verify it appears on the board. Then close it via status update. Is the creation → placement → status flow clear from the tool descriptions alone? Check for any partial failure signals in the response and report them.

**Scenario 5.6 — Log an impediment**
Log a blocking impediment (orphan — not linked to a specific story). Verify it appears when searching for impediments. Then progress it through its full lifecycle: open → in progress → resolved. Is the impediment workflow clearly separated from the general story workflow, and does it feel natural for a SM to use?

**Scenario 5.7 — Bulk sprint planning**
Pick 2–3 backlog items. Assign them to the current sprint in one call. Verify all are assigned. Then revert each back to the backlog. Does the bulk tool feel more efficient than calling the single-field setter per item?

---

### PHASE 6 — TEMPLATES & RESOURCES

**Scenario 6.1 — Use a template**
From your orient result, check whether templates are configured. If yes, read a template for one item type. Is the template content useful? Is reading it via a resource URI intuitive, or would you expect this to come back from a tool call instead?
